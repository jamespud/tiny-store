# 字节商城用户认证系统设计文档

## 1. 文档概述

### 1.1 文档目的

本文档详细描述字节商城用户认证系统的设计方案，包括架构设计、功能模块、流程逻辑、安全机制等，为开发、测试、运维提供技术指导。

### 1.2 范围定义

- **覆盖场景**：用户注册、登录（含跨端登录）、身份验证、权限授权、令牌管理、账号安全等。
- **边界说明**：仅包含C端用户（消费者）认证，不涉及B端商家认证；依赖字节跳动统一账号中台，本文档聚焦商城侧的适配与扩展。

### 1.3 目标读者

开发工程师、测试工程师、系统架构师、产品经理。

### 2.2 层级说明

1. **前端层**  
   负责用户交互与登录状态管理，包括登录入口展示、授权弹窗渲染、本地令牌存储（如`localStorage`
   ）、登录状态同步（跨页面/跨端）。

2. **后端服务层**
    - **商城认证适配服务**：作为商城与字节统一认证中心的中间层，处理登录请求转发、令牌解析、权限校验等。
    - **字节统一认证中心**：字节账号中台核心组件，提供身份验证、令牌生成、权限管理等基础能力（复用集团基建）。
    - **权限引擎**：管理商城所需的权限项（如`address`/`phone`），校验接口调用的权限合法性。
    - **风控引擎**：实时评估登录/操作风险，触发二次验证或异常拦截（对接字节全域风控系统）。

3. **数据层**
    - 存储商城侧用户关联数据（如`openid`与商城用户ID映射）、加密的令牌信息、脱敏的用户基础数据（昵称、头像）及全量操作日志。

## 3. 核心功能模块设计

### 3.1 统一认证中心（复用字节账号中台）

#### 3.1.1 功能描述

提供标准化的身份验证与令牌管理能力，支持多端登录、跨产品身份互通。

#### 3.1.2 核心组件

- **身份验证模块**：支持手机号验证码、密码、人脸识别、第三方账号（微信/支付宝）等验证方式。
- **令牌服务**：生成/验证ID Token、Access Token、Refresh Token，维护令牌生命周期。
- **用户信息接口**：提供标准化的用户信息查询（如`/user/profile`获取昵称头像，`/user/address`获取地址）。

#### 3.1.3 技术实现

- 基于OIDC 1.0协议实现身份验证，OAuth 2.0协议实现权限授权。
- 令牌采用JWT（ID Token）+ 随机字符串（Access Token）混合方案，兼顾可读性与安全性。

### 3.2 商城认证适配服务

#### 3.2.1 功能描述

作为商城与统一认证中心的桥梁，处理商城专属的认证逻辑与适配需求。

#### 3.2.2 核心功能

- **登录流程适配**：根据商城场景（如购物车下单前强制登录）触发登录，跳转统一认证中心并处理回调。
- **令牌解析与存储**：接收认证中心返回的令牌，验证ID Token签名，提取`openid`并关联商城用户ID，加密存储Refresh
  Token。
- **权限映射**：将商城业务权限（如“获取支付信息”）映射为认证中心的标准权限项（如`scope=payment`）。
- **会话管理**：维护商城本地会话状态（如登录态过期时间、设备绑定），同步认证中心的令牌失效事件。

#### 3.2.3 关键逻辑

```python
# 伪代码：令牌解析与用户关联
def handle_auth_callback(id_token, access_token, refresh_token):
    # 1. 验证ID Token签名（使用字节公钥）
    if not verify_id_token_signature(id_token, byte_pub_key):
        raise AuthException("ID Token验证失败")
    
    # 2. 解析用户信息
    payload = decode_jwt(id_token)
    openid = payload["sub"]
    nickname = payload["name"]
    avatar = payload["picture"]
    
    # 3. 关联商城用户ID（首次登录自动创建）
    user_id = get_or_create_mall_user(openid, nickname, avatar)
    
    # 4. 存储令牌（Access Token内存缓存，Refresh Token加密入库）
    cache.set(f"access_token:{user_id}", access_token, 7200)  # 2小时
    db.save_refresh_token(
        user_id=user_id,
        token=encrypt(refresh_token, aes_key),  # 加密存储
        expire_time=30天后期
    )
    
    # 5. 返回商城会话凭证
    return generate_mall_session(user_id)
```

### 3.3 权限引擎

#### 3.3.1 功能描述

管理用户对商城资源的访问权限，确保“最小必要”原则落地。

#### 3.3.2 权限定义（电商场景专属）

| 权限编码      | 权限名称   | 申请场景      | 权限等级 | 过期策略        |
|-----------|--------|-----------|------|-------------|
| `profile` | 基础信息   | 登录时默认获取   | 基础   | 永久有效（除非撤销）  |
| `phone`   | 手机号    | 订单通知、物流联系 | 敏感   | 180天（需重新确认） |
| `address` | 收货地址   | 下单填充地址    | 敏感   | 180天（需重新确认） |
| `follow`  | 抖音关注关系 | 推荐关注商家商品  | 敏感   | 90天（需重新确认）  |
| `payment` | 支付账户信息 | 快捷支付      | 高敏感  | 30天（需重新确认）  |

#### 3.3.3 权限校验流程

1. 商城后端接口调用前，检查请求携带的Access Token。
2. 调用认证中心`/token/introspect`接口，解析Token包含的`scope`（权限范围）。
3. 比对接口所需权限（如地址接口需`address`）与Token的`scope`，不匹配则返回403。

### 3.4 风控与安全模块

#### 3.4.1 风险评估维度

| 维度   | 风险指标                   | 高风险阈值示例             |
|------|------------------------|---------------------|
| 设备风险 | 新设备登录、Root/越狱设备        | 首次使用的设备占比≥80%       |
| 位置风险 | 异地登录（与常用IP地区不符）、IP在黑产库 | 1小时内跨3个省份登录         |
| 行为风险 | 登录频率异常、操作路径偏离用户习惯      | 10分钟内登录失败≥5次        |
| 令牌风险 | Token在异常环境使用（如黑产设备）    | Token与历史设备指纹匹配度＜30% |

#### 3.4.2 风险响应策略

- **低风险**：正常登录，记录风险日志。
- **中风险**：触发二次验证（如短信验证码）。
- **高风险**：临时冻结账号（15分钟），提示用户通过安全中心解封。

└────┬────┘     └────┬────┘     └────┬────┘     └────┬────┘

     │                │                │───────────────►│

### 4.2 权限申请流程（以“获取收货地址”为例）

1. 用户在商城下单，点击“选择地址”，触发权限检查。
2. 商城后端发现用户未授权`address`权限，返回“需授权”标识。
3. 前端弹窗展示权限申请说明（“为快速下单，需获取您的收货地址”），用户点击“同意”。
4. 商城后端向认证中心发起授权请求（`scope=address`），跳转授权页。
5. 用户确认授权后，认证中心返回新的Access Token（包含`address`权限）。
6. 商城后端用新Token调用`/user/address`接口，获取地址并展示。

## 6. 安全策略

### 6.1 身份验证安全

- **多因素验证**：高风险操作强制人脸识别/短信验证，确保“操作人=账号所有人”。
- **密码策略**：若用户使用密码登录，强制密码复杂度（8-20位，含大小写+数字+符号），定期提醒更换。
- **防暴力破解**：同一账号10分钟内登录失败≥5次，临时锁定30分钟。

### 6.2 令牌安全

- **ID Token**：签名验证（防篡改）、有效期校验（2小时）、`iss`（签发者）校验（仅信任`accounts.bytedance.com`）。
- **Access Token**：内存缓存（不落地存储）、传输加密（HTTPS）、定期自动刷新（过期前30分钟）。
- **Refresh Token**：加密存储（AES-256）、绑定设备指纹（仅允许首次生成的设备使用）、用户主动登出时立即失效。

### 6.3 数据安全

- **敏感信息脱敏**：手机号存储为`138****5678`，地址隐藏门牌号，支付信息不落地存储（仅临时调用）。
- **权限最小化**：商城后端仅存储`openid`/昵称/头像等基础信息，敏感信息（如手机号）需实时调用认证中心接口获取，不本地缓存。
- **日志安全**：操作日志不含明文令牌/密码，仅记录`user_id`/操作类型/时间/IP，日志权限严格管控（仅审计人员可查）。

## 7. 接口设计（核心API）

### 7.1 商城侧接口

#### 7.1.1 触发登录接口

- **请求**：`GET /api/auth/login?redirect_uri=https://mall.bytedance.com/callback`
- **响应**：`302 Redirect` 至认证中心授权页

#### 7.1.2 认证回调接口

- **请求**：`GET /api/auth/callback?id_token=xxx&access_token=xxx&refresh_token=xxx`
- **响应**：
  ```json
  {
    "code": 0,
    "data": {
      "user_id": 123456,
      "nickname": "张三",
      "avatar_url": "https://xxx.com/avatar.jpg",
      "session_id": "sid_abc123"  // 商城本地会话ID
    }
  }
  ```

### 7.2 认证中心接口（复用字节标准接口）

- **令牌验证**：`POST /oauth2/introspect`（校验Access Token有效性及权限）
- **刷新令牌**：`POST /oauth2/token?grant_type=refresh_token&refresh_token=xxx`
- **用户信息**：`GET /userinfo?access_token=xxx`（返回授权范围内的用户信息）

## 8. 部署与运维

### 8.1 部署架构

- **多活部署**：商城认证适配服务部署在多可用区，避免单点故障。
- **缓存策略**：Access Token缓存在Redis集群（主从+哨兵），确保高可用。
- **数据库**：核心表（`mall_user`/`user_token`）采用MySQL主从架构，支持读写分离。

### 8.2 监控与告警

- **核心指标**：登录成功率（≥99.5%）、令牌验证成功率（≥99.9%）、接口响应时间（P99≤100ms）。
- **告警触发**：指标异常（如登录成功率＜95%）、接口错误率突增（≥1%）、风控拦截量异常波动。

### 8.3 容灾备份

- **数据备份**：数据库每日全量备份+实时增量备份，备份数据保留30天。
- **故障转移**：认证中心不可用时，临时降级为“仅支持手机号验证码登录”（本地验证，后续同步状态）。

## 9. 附录

### 9.1 术语表

- **openid**：用户在商城内的唯一标识，由认证中心颁发。
- **unionid**：用户在字节生态内的唯一标识，用于跨产品识别同一用户。
- **ID Token**：包含用户身份信息的JWT令牌，用于身份验证。
- **Access Token**：用于调用用户信息接口的授权令牌，含权限范围。
